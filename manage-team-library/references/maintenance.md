# 维护与共享

目标团队以本次请求、工作区 origin 和现有 TeamAI 绑定为准。只查看工具时读取 `skill-catalog.json` 与候选描述，不先触发升级或全库检查。空清单如实说明尚无业务 Skill。

## 内容与职责

团队长期共同要求放根 `AGENTS.md`；某类可复用方法放 `skills/<名称>/` 并登记 `skill-catalog.json`；确有需要才增加 Core 支持的 `agents/`。项目要求留在相应项目，一次性指令留在当前对话。外置助手不进入团队 Skill 清单，也不占用团队同步管理权。

修改在独立创作检出目录中进行，已安装副本和 TeamAI 缓存仅供读取。个人规则放受管标记外，运行数据放 Skill 的 `.runtime/`。不把原始客户资料、账号和运行数据共享进仓库。

## 更新已发布的团队内容

```text
node scripts/team-library.mjs update --repo OWNER/REPO --workspace ABSOLUTE_PATH --agent HOST
```

这会调用现有受保护的 TeamAI pull，不上传个人改动、不更新创作分支、不升级 Core。只要求更新单包时说明 Core 实际更新本团队资源；没有单包同步保证。避开正在使用受影响资源的任务，更新后用新对话确认加载。

失败区分为：依赖缺失、账号或邀请、错误团队、版本不符、文件冲突、宿主未加载、业务质量。只处理对应原因。源码冲突与损坏的受管标记不能靠强制覆盖解决；更新失败保留原有文件。

## 整理方法、规则与角色

1. 读取本团队最新 README、`teamai.yaml`、Core 锁、相关代码与当前 Git 状态。按现有授权建工作分支，保留无关改动。
2. 从实际任务和认可结果整理方法，不让成员填写专业表单。已有同类入口优先修改；只影响一个项目的要求不扩大到全团队。
3. Skill 至少有包含 name/description 的 `SKILL.md`，名称与目录一致，写清必要输入、关键做法、结果和适用范围。仅为真实需要增加参考、脚本或素材。没有宿主的 skill-creator 时也可完成，不依赖其他预装业务 Skill。
4. 团队模板运行 `npm run validate`、`npm test`；新增脚本实际执行，方法与入口用匹配请求试用。涉及同步、路径或版本时再运行 `npm run test:e2e`。只准备改动涉及的依赖，不让改一篇方法先安装所有业务工具。

## 提交、审核、发布

“提交给团队”表示提交审核，不等于合并发布。只暂存本次已核对文件，提交工作分支并普通 push；不强推。用 `gh pr create --body-file` 提交说明，已存在对应 PR 时更新同一项，不重复创建。说明具体变化、影响、已执行检查与缺口。

负责人核对候选内容、真实 GitHub 权限和检查后，按明确发布授权合并。CI 存在不等于强制门禁已配置；检查没运行不能算通过。其他成员正常更新后才获得已合并改进。Agent 的 GitHub 身份始终是当前授权用户。

停止使用某个共享方法时检查引用，删除源包并更新清单，经同一审核流程发布。个人修改与运行数据可能阻止本机移除，应保留并整理。恢复优先撤回具体错误改动后检查和发布，不重置共享历史。

## 助手与 Core 的升级

团队内容更新、外置助手更新、Core 升级是不同操作。外置助手从同一公开发布源取得固定版本，核对摘要，从新下载目录运行 `install --agent HOST`；收据校验发现本地修改会停止，不覆盖。团队不能通过共享 Skill 重新分发同名助手。宿主当前会话不会自动切换到新规则。

Core 仅在用户要求升级时采用新锁定版本，检查 package.json、package-lock.json、Core 锁的一致性，并验证同步、冲突、个人内容保护和恢复。不修改 node_modules，不将整个模板覆盖公司内容。

修订这个通用助手时，在它自己的源码仓库提交审核；修订公司方法时在公司仓库提交。助手对项目的描述应引用真实文件与已验证行为，不复制一套会过期的团队配置。
